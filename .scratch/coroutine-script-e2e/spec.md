# Java 真实脚本协程验收用例

Label: ready-for-agent
Type: specification
Status: implementation-in-progress


## Problem Statement

现有真实脚本用例以启动和互操作检查为主，不能证明协程的结果、错误、取消、上下文和关闭行为。入口可调用或出现成功日志不足以证明异步工作完成。

## Solution

在本项目维护可重复运行的真实脚本用例，使用 Test Control 提交并验证脚本断言、运行终态和清理结果，以公开行为证明协程契约。

## User Stories

1. 作为 Java 脚本作者，我希望真实脚本能创建并组合异步任务，以便示例可直接作为使用依据。
2. 作为测试维护者，我希望每个用例有稳定身份和有限超时，以便失败能被准确定位。
3. 作为测试维护者，我希望每个公开方法映射到实际断言，以便覆盖范围可审查。
4. 作为脚本作者，我希望结果、nullable 和集合传递都有断言，以便桥接转换不会悄悄损坏值。
5. 作为脚本作者，我希望异常、恢复和取消分别验证，以便失败语义清晰。
6. 作为脚本作者，我希望延迟、结果链与嵌套回调后仍可使用语言对象，以便异步恢复可靠。
7. 作为脚本作者，我希望 Thread/Timer 与协程组合有真实例子，以便知道如何安全混用。
8. 作为测试维护者，我希望完成前后注册通知都被验证，以便不依赖同步通知的偶然实现。
9. 作为脚本作者，我希望 Flow 与通道的值、顺序和清理有断言，以便流水线可以维护。
10. 作为测试维护者，我希望关闭阶段失败使验收失败，以便打印成功后泄漏资源不算通过。
11. 作为测试维护者，我希望区分脚本断言、运行错误、超时和基础设施失败，以便正确排查。
12. 作为测试维护者，我希望测试源码不进入产品主发布产物，以便验收资产保持隔离。
13. 作为测试维护者，我希望使用已有选择任务运行受影响用例，以便回归快速且可重复。
14. 作为测试维护者，我希望不可观察行为明确记为缺口，以便不伪造通过证据。

## Implementation Decisions

- 首先通过本项目不依赖协程的 Thread/Timer 真实脚本基线，再启动协程验收；使用原有脚本调用形状，不给调用者增加上下文参数或手动绑定。
- 基线覆盖线程任务、timeout/immediate、interval 多轮与清除、语言对象及参数、异常、嵌套和最终清理；运行终态与清理同样是门槛。

- 用例由本项目持有，使用实际语言语法与桥接方式；共享的是行为要求，不引入运行时读取其他源码树的依赖。
- 按现有 manifest 和文件式脚本组织方式新增场景，不把大型脚本内嵌为 JSON 字符串。依赖身份与版本以本项目当前配置为准。
- 使用现有 Test Control 任务选择场景，不编写语言专属远程执行器或直接解析 logcat 判定通过。
- 脚本先对精确值、事件顺序或终态断言，最后才输出标记；expectedLogs 只是附加断言，最终响应和清理仍是必要条件。
- 任务完成与通知排空分开等待；使用有限事件等待，不靠固定 sleep、随机竞争或完全匹配偶然线程名。
- 上下文安装与恢复的故障注入若不能由普通脚本公开入口稳定构造，则标明对应的运行边界证据需求；不增加测试专用脚本方法。
- 编写逐方法证据清单，覆盖继承方法；原生宿主互操作明确排除普通脚本证据并解释理由。
- 测试只拥有其创建的任务、监听器和临时资源；在清理路径注销并取消，不删除产品项目目录或遗留全局修改。

## Testing Decisions

- 最高边界为真实 Android 设备上的脚本执行。对每个场景分别记录断言结果、脚本终态、清理状态和结构化报告。
- 行为场景包含：公开入口与同步配置、任务与结果链、异常与恢复、取消、等待与执行权、调度与线程约束、嵌套进入、Thread/Timer 与协程混合、完成通知、通知异常、续体与取消通知、流创建与转换、流终端、流异常与结束、背压与时间、通道与回调流、所有权与关闭、句柄与注销。
- 附着/恢复故障和关闭超时记录适当边界证据；无法由本项目脚本观察的内容保留 observation-gap，不能列为 direct-e2e。
- 先通过现有 Selected 任务运行最小相关用例，再运行本项目完整 Test Control 集；实际命令在执行时核对，当前没有运行结果。
- 记录执行版本与真实进程身份，超时保留最后已知事件和清理状态；基础设施失败不得改写为业务通过。

## Out of Scope

不实现语言运行时或通用调度机制，不扩展协议字段来承载协程业务，不重构无关模板内容，不用单纯语言启动检查替代协程验收。
