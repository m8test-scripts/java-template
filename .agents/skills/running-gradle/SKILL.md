# 运行 Gradle

先从仓库根目录使用项目 Wrapper，并确认目标任务及它的实际范围。用户只要求 IDE/Gradle sync 时选择配置或帮助任务，不扩大为编译、测试或设备操作。

- 每条命令使用 `./gradlew --no-daemon`，让本次构建结束后由本次命令启动的 Gradle 构建 JVM 退出并释放其内存。`--no-daemon` 本身不限制内存；Gradle 可能仍为本次构建启动一次性 daemon。不要运行 `--stop`，也不要停止 IDE、用户或其他会话启动的进程。若环境或任务确实要求复用 daemon，说明原因；不要声称构建结束时该 daemon 已退出。
- 每条命令都显式为 Gradle 构建 JVM 设置较低的初始堆和有界的最大堆，例如 `-Dorg.gradle.jvmargs="-Xms256m -Xmx1536m"`。按任务预计用量和系统可用内存选上限：帮助、配置查询等轻任务可从 `-Xmx512m` 起；常规编译或测试可从 `-Xmx1536m` 起；大型 Android 构建只有在任务范围和内存余量支持时才从 `-Xmx2g` 或更高值起步。数值是起始建议，不是硬性任务分类。`-Xmx` 限制 Java 堆，不代表整个进程的 RSS 上限；保留项目必需的 JVM 参数，不把上限设为机器全部可用内存。
- 内存不足时，先确认错误确属 OOM/堆不足并区分 Gradle JVM、Kotlin daemon、测试 JVM或其他 worker，再针对对应进程逐级提高上限并重试。每次只增加必要的额度，同时留出操作系统和其他应用需要的内存；不因普通构建失败就直接大幅提高上限。
- Kotlin 编译可能启动独立 Kotlin daemon，它会增加总内存占用。编译 Kotlin 时检查并显式限制 `kotlin.daemon.jvmargs`（例如命令追加 `-Pkotlin.daemon.jvmargs=-Xmx768m`）；结合 Gradle JVM 与 Kotlin daemon 的上限评估总用量。项目配置已给出 JVM 参数时，在保留必要参数的基础上形成有效上限，不要覆盖掉编码、模块开放等必需选项。测试任务还要计入 fork 出来的测试 JVM；worker 限制不等于这些进程与 Gradle 共用一个堆。
- 一次只运行一个由本会话启动的 Gradle 命令，结束后确认该命令及其一次性构建进程已退出，再启动下一条；同一代理会话只保留一个正在运行的 Gradle 构建。使用 `--no-parallel` 和 `--max-workers=1`，避免并行任务和 worker 放大内存峰值。
- 将标准输出和错误输出限制在便于排错的摘要。优先 `-q`；需要保留完整诊断时写入任务专属日志文件，只提取失败任务、错误原因及必要上下文。成功时简要报告任务和结果，不打印全量日志。
- 设备、安装或发布任务仅在用户请求或当前授权流程需要时执行，并遵循仓库规定的设备选择方式。
- 失败时先检查对应测试报告、lint 报告或任务报告，再查看错误附近日志；仅在摘要不足以定位时查看更详细堆栈。
